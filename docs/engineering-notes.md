# Implementation Notes

In America/Asuncion, 2023-10-01 has no 00:00 and starts at 01:00. Simply adding days to the month start propagated 01:00 to later cells and the query end. Each date must be normalized with startOfDay so the first hour outside the displayed range is not queried. A regression test reproduces this case.

Top-level code in a Swift Package executable is not treated as main actor under the current language settings. Initialize the main-actor app delegate in an explicit main actor context, and retain the delegate for the duration of NSApplication.run.

For a menu-bar-only app with no regular window, the computer-use tool's app selection can end in timeoutReached. A temporary verification window was added to check the UI and removed from the final build. The popover must be verified by clicking the real menu bar icon.

Running the app binary directly from a terminal can attribute calendar permission's responsible process to the launching tool. Real-account verification is done by opening the app bundle from Finder. Do not assume existing calendar access survives an ad-hoc re-sign.

On this Mac, the first development run bound CalendarBar to Orca's menu bar display entry. The status button window was created at (0,-22,38,22) with screen=nil, so the original implementation opened the popover at the bottom-left of the screen. It now opens only when valid screen coordinates exist. On 2026-09-28, inside the binary plist in the `trackedApplications` Data of ControlCenter's group preference, the Orca entry's `menuItemLocations` was confirmed to store the normal, QA, and Runtime QA CalendarBar identifiers together. This matched system logs showing that turning Orca off also blocked the normal and QA hosts, independent of each CalendarBar entry's `isAllowed=true`. At 17:42 the original Data was backed up to local `.dryforge/backup` with permissions 0600; original identity was checked immediately before writing, and only the single key at the exact preference file path was updated with `defaults write`. Only the three CalendarBar links in the Orca entry were removed, and the remaining structure, allowed states, and other keys were confirmed unchanged and persisted on a separate re-read. No full settings reset or ControlCenter restart was performed. Then, with Orca display off, toggling the normal app's own display off and on produced 17:57:46 blocked and 17:57:53 unblocking→tracking logs. Final settings were Orca=false, CalendarBar=true, with their stored links separated. A canonical Runtime QA rerun under the same conditions did not recreate the link, and the parent verifier confirmed the real QA popover and showSucceeded before exiting. At 18:05, after relaunching the existing Applications install normally without file changes, the Orca link was still not recreated. The new normal process registered in ControlCenter in the order Starting to track host→Created new displayable type→Adding displayable items, and its name changed from the initial Item-0 to CalendarBar.date. The normal app's personal-event popover was not captured, so QA's screen check is not extended to a normal-account popover check. Persistence after re-login or reboot is unverified. Whether the current process's responsible PID or ad-hoc signing caused this stored link was not determined.

Swapping only the month data at drag end makes the calendar change abruptly. Separate the visual offset from the actual selected month and change the month exactly once when the animation completes. Reopening or moving to another date invalidates the previous transition's completion callback. If a page's date and event data are unchanged, date buttons and dots are not redrawn, reducing repeated formatter creation during drags.


If invalidating a query channel only bumps a global generation, another in-flight range can stay loading forever or an old response can overwrite a new result. Direct occurrence checks without a range must also recheck permission and calendar selection. Interleavings of channel, request generation, and permission changes are pinned with fake-backend regression tests.

A reminder query failure is not deletion. However, explicit turn-off, hide, privacy cleanup, and safe cancellation of corrupted settings must be independent of failures. Isolate by occurrence basis so ambiguity in one recurrence does not cancel other occurrences' schedules, and check delivered reminders separately.

A SIGABRT in `swift_task_dealloc` was reproduced when canceling/resetting the reminder timer's default `Task.sleep(for:)`. After switching to the nanoseconds overload, regression tests for 100 resets/cancellations and weak release passed. The root cause inside the Swift runtime was not determined.

For detached recurring occurrences in real EventKit, deletion and a distant move cannot be distinguished with a single range. Out-of-range results from direct checks are not treated as deletion; only definite series keys are used as link evidence and the rest stay needs confirmation. Combinations of cancellation, detachment, and distant moves on a real account need separate verification.

In this execution environment, checking an exited child's group with `os.killpg(group, 0)` raised EPERM instead of ESRCH. Reproduced with a time-limited run of `/bin/sleep`. EPERM is not ignored; termination is concluded only when a separate `ps` listing has no members of that group. If members exist or the listing fails, a cleanup failure is reported. A real-process test that kills grandchildren ignoring SIGTERM and confirms the group is gone is kept.


In the Upcoming list, when a per-date `ForEach` under `LazyVStack` expanded the same ID of a multi-day occurrence multiple times, the next date's rows vanished into empty space. The synthetic event's 9/28 row was visible, but the two 9/29 rows were absent from AX and rendered blank. After switching to row IDs combining date and occurrence, titles and bell buttons appeared on both dates in the real popover. This rendering bug was not caught by data calculation tests alone.

The computer-use tool can return stale elements from an inactive QA window. Read the latest state after raising the regular window, and recheck the current screen if an index is invalid. Do not treat a closed popover whose accessibility tree lingers as an open view.


Building only one kind of original occurrence basis from a recurring occurrence's current all-day flag misses stored rules after a timed↔all-day change. Keep both instant and civil date evidence in memory from EventKit's original occurrence time and match against the same kind as the stored rule. If multiple occurrences of the same series fall on one civil date, mark that date evidence as ambiguous. An exact-time per-event override takes precedence, and editing or scheduling success is never claimed on an ambiguous date basis alone.

Even when the future rule is edited from an occurrence earlier than the new boundary, the existing series' boundary representation must be continued. Mixing instant and civil boundaries leaves old rules behind or makes order incomparable, so mixed replacement is rejected. Clearing an override also uses the stored override's identity and anchor instead of the draft's current format. This dual evidence for lookup is not stored, and the version 1 structure of the reminder settings file did not change.

After a user report that clicking a reminder only launched the process with nothing on screen, failing tests reproduced the loss of the first show request when menu bar position/activation was not ready and the reopen path resetting the destination. Show readiness waits up to 40 times at 50ms intervals and is canceled on close, deactivation, or a new request. A normal reopen returns to today, but reopens during reminder handling and for only 2 seconds after completion are treated as the same request. Because AppKit's reopen callback lacks the original request kind, a Finder reopen in this short window can also preserve the destination. An explicit menu open clears this state immediately. In real runs, the strict `isActive` precondition caused an accessory app with no regular window to keep waiting for activation. Fixed by performing popover show·makeKey first at a valid menu bar anchor and then requesting activate. In the current session, a cold OS click showed after about 0.41 seconds via limited retries following an initial show failure, and the user confirmed the screen appeared. A warm click succeeded in the same PID, and the user confirmed the target date and row highlight. This is not extended to a separate confirmation of the cold click's target date and row highlight on the real screen.
